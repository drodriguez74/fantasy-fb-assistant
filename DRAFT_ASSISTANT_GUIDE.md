# Live Draft Assistant Guide

## Overview

The Fantasy Football Assistant includes real-time draft assistance for **ESPN**, **Yahoo**, and **Sleeper**. This guide was rewritten against the actual current code (`backend/app/api/v1/endpoints/live_draft.py`, `backend/app/services/draft_assistant_service.py`, `backend/app/services/consensus_ranking_service.py`, `backend/app/services/scoring_rules.py`, `backend/app/api/v1/endpoints/league_scoring.py`, `backend/app/services/ai_service.py`) rather than aspiration — several important things changed or were never quite what an earlier version of this doc claimed. The most significant correction: **the real API mount point is `/api/v1/draft/live-draft/...`, not `/api/v1/live-draft/...`.** Every example below uses the real path.

## Features

### Real-Time Draft Assistance
- Live pick recommendations based on your actual roster needs, generated by a single DEEP-tier AI call (top-3 picks with reasoning + confidence) — see "AI Recommendations" below for exactly which model/pipeline this is (it is *not* the 5-perspective/consensus pipeline; that pipeline powers blog/waiver-post content generation instead — see that section for why this matters)
- Value-pick and sleeper identification from real consensus rankings (see "Consensus Ranking System")
- Positional tier rankings

### Platform Integration (real status per platform)
- **Sleeper**: fully live, backed entirely by Sleeper's public API — no auth needed against Sleeper itself (a valid app JWT is still required to call this app's own endpoints)
- **ESPN**: fully live via per-user session cookies (`espn_swid` / `espn_s2`) — required for private leagues, optional for genuinely public ones. Cookies live on the caller's own `UserLeague` row, not shared/global state.
- **Yahoo**: fully live via per-user OAuth2 access token, same per-user storage model as ESPN's cookies. **Known current limitation:** Yahoo login is presently blocked by a real external configuration issue — the founder's Yahoo Developer app console has a redirect URI that doesn't match what this app sends, so the OAuth consent flow fails before a token is ever issued. This is not a bug in this codebase; it needs a fix in Yahoo's own app console. `GET /api/v1/leagues/yahoo/test-credentials` confirms `YAHOO_CLIENT_ID`/`YAHOO_CLIENT_SECRET` are present and correctly loaded — the credentials are configured, the redirect URI registered with Yahoo is what's wrong.

### Consensus Ranking System (new)
Blends up to **four** independent ranking signals via `consensus_ranking_service.py` — see "Consensus Ranking System" below.

### Real Per-League Scoring Rules (new)
Draft recommendations now reason about a connected league's *actual* scoring rules — pass completions/incompletions, INTs, fumbles lost, etc — not just PPR-vs-Standard. See "Real Per-League Scoring Rules" below.

### Manual Scoring Override (new)
Users can hand-configure scoring rules for a league via `POST /api/v1/league-scoring/configure`, and the draft assistant will use that configuration in place of (or on top of) whatever it auto-detected from the platform. See "Manual Scoring Override" below.

## Getting Started

### 1. Start a Draft Session

The real endpoint requires authentication (a Bearer token from `/api/v1/auth/login`) — an earlier version of this guide showed this call with no `Authorization` header, which no longer works.

```bash
curl -X POST "http://localhost:8000/api/v1/draft/live-draft/start-session" \
  -H "Authorization: Bearer YOUR_TOKEN_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "league_id": "123456",
    "platform": "sleeper",
    "scoring_format": "PPR",
    "league_size": 12,
    "user_team_id": "1"
  }'
```

For `platform: "espn"` or `platform: "yahoo"`, the league must already be connected through that platform's real connect flow (see "Platform-Specific Setup" below) — `league_id` here is looked up against the caller's own `UserLeague` rows (`UserService.get_user_league_by_platform_id`), not passed straight through to the platform. If no matching connected league is found, the endpoint returns a 400 with an explicit "connect your league first" message rather than a vague failure. For Yahoo specifically, `league_id` is transparently swapped for the stored `league_key` (Yahoo addresses leagues by a composite key like `"449.l.12345"`, not the bare numeric id).

**Response shape** (fields present in the real code — `session_id`/`draft_state`/`initial_recommendations`/`status` from `draft_assistant_service.start_draft_session`, plus `platform`/`league_id`/`real_espn_league` added by the endpoint):
```json
{
  "session_id": "sleeper_123456_1234567890.123",
  "draft_state": {
    "status": "drafting",
    "current_pick": 15,
    "available_players": [...],
    "trending_players": [...],
    "picks": [...],
    "league_settings": {...}
  },
  "initial_recommendations": {
    "recommendations": [
      {"player_name": "...", "position": "RB", "reasoning": "...", "confidence": 85}
    ]
  },
  "status": "active",
  "platform": "sleeper",
  "league_id": "123456",
  "real_espn_league": false
}
```

### 2. Get Live Recommendations

```bash
curl "http://localhost:8000/api/v1/draft/live-draft/recommendations/{session_id}"
```
Returns whatever `draft_assistant_service.get_live_recommendations` produces for the session — the shape is driven by `ai_service.generate_draft_recommendation`'s real JSON contract: `{"recommendations": [{"player_name", "position", "reasoning", "confidence"}, ...]}`, plus value/sleeper picks computed locally from consensus rankings (not from the AI call). This endpoint does **not** require the `Authorization` header in the current code (only `/start-session` does) — worth knowing but not something to rely on, since it means anyone who learns a `session_id` can currently poll it.

### 3. WebSocket Connection for Real-Time Updates

```javascript
const ws = new WebSocket('ws://localhost:8000/api/v1/draft/live-draft/ws/{session_id}');

ws.onmessage = function(event) {
    const data = JSON.parse(event.data);
    if (data.type === 'recommendations_update') {
        updateDraftBoard(data.data);
    } else if (data.type === 'pick_update') {
        refreshUserRoster(data.data);
    }
};
```
The server pushes a `recommendations_update` every 10 seconds automatically (`asyncio.sleep(10)` loop in `live_draft.py::websocket_endpoint`) and a `pick_update` immediately after any `POST .../update-pick`. This part of the doc was already accurate and is unchanged, other than the path prefix.

The real frontend confirms this exact mount point in its own source comment (`frontend/src/pages/LiveDraftPage.tsx`):
```ts
// The live-draft router is mounted at /draft/live-draft (see
// backend/app/api/v1/router.py)
const LIVE_DRAFT_API_PREFIX = '/draft/live-draft'
```

## Platform-Specific Setup

### Sleeper

Sleeper's API is genuinely public — no OAuth, no cookies. Two ways to use it:

1. **Directly**, with no prior connect step — just pass a Sleeper `league_id` to `/start-session` with `platform: "sleeper"`.
2. **Connected** first via `POST /api/v1/leagues/sleeper/connect` (requires your app auth token), which validates the league against Sleeper's real API, optionally resolves which roster is yours from a Sleeper username, and persists it as a `UserLeague` row. Connecting isn't required for the live draft assistant to work, but it is required for the manual scoring-override system (`league-scoring/configure` needs a real `UserLeague.id`) and for the league to show up in `GET /api/v1/draft/my-leagues`.

```bash
curl -X POST "http://localhost:8000/api/v1/draft/live-draft/start-session" \
  -H "Authorization: Bearer YOUR_TOKEN_HERE" \
  -H "Content-Type: application/json" \
  -d '{"platform": "sleeper", "league_id": "123456789"}'
```

### ESPN Fantasy Football

An earlier version of this guide said "ESPN leagues are publicly accessible — no authentication required!" That's only true for genuinely public leagues, and even then only for the standalone debug endpoints below — it is **not** true for the real live-draft flow, which requires a connected league regardless:

```bash
curl -X POST "http://localhost:8000/api/v1/leagues/espn/connect" \
  -H "Authorization: Bearer YOUR_TOKEN_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "league_id": "123456",
    "season": 2026,
    "swid": "{YOUR-SWID-COOKIE}",
    "espn_s2": "YOUR_ESPN_S2_COOKIE",
    "team_id": "1"
  }'
```
`swid`/`espn_s2` are optional in the request — omit them for a genuinely public league. They're required for a private one; ESPN returns an auth error from `espn_service_enhanced.connect_league` otherwise, surfaced as a 400. `GET /api/v1/leagues/espn/teams?league_id=...` lets the user pick which team is theirs before connecting (needed for roster/matchup analysis to know "your" team).

Once connected, `/api/v1/draft/live-draft/start-session` with `platform: "espn"` looks up the stored cookies from your `UserLeague` row automatically — you never pass ESPN credentials to the live-draft endpoints directly.

Separately, three standalone debug endpoints still exist under the live-draft prefix and call the older, plain `espn_service.py` (not the `_enhanced` version the real connect flow uses) with **no credentials at all** — these only work against genuinely public leagues and are not part of the real per-user flow:
```bash
curl "http://localhost:8000/api/v1/draft/live-draft/espn/leagues/123456/info"
curl "http://localhost:8000/api/v1/draft/live-draft/espn/leagues/123456/teams"
curl "http://localhost:8000/api/v1/draft/live-draft/espn/leagues/123456/draft"
```

### Yahoo Fantasy Sports

The real, current Yahoo flow is `POST /api/v1/leagues/yahoo/connect`, not the `live-draft/yahoo/*` endpoints an earlier version of this guide described:

1. **Get the authorization URL** (built server-side so the client id/redirect are never hardcoded in the frontend):
   ```bash
   curl "http://localhost:8000/api/v1/leagues/yahoo/auth-url"
   ```
2. User completes Yahoo's consent screen; the frontend's OAuth callback page relays the `authorization_code` back via `postMessage`.
3. **Exchange the code and persist the connection** — this single call exchanges the code for a real access/refresh token pair, fetches the user's actual Yahoo leagues, and persists one `UserLeague` row per league (with the token, refresh token, and expiry) scoped to the calling user:
   ```bash
   curl -X POST "http://localhost:8000/api/v1/leagues/yahoo/connect" \
     -H "Authorization: Bearer YOUR_TOKEN_HERE" \
     -H "Content-Type: application/json" \
     -d '{"authorization_code": "AUTH_CODE_FROM_STEP_2", "redirect_uri": "http://localhost:3001/yahoo/callback"}'
   ```
4. `/api/v1/draft/live-draft/start-session` with `platform: "yahoo"` then looks up the stored token automatically. Yahoo tokens are short-lived (~1 hour, unlike ESPN's long-lived cookies); an expired token is rejected honestly at session start with a "reconnect your Yahoo account" message rather than failing later with a cryptic error mid-draft. There's no silent token refresh — refreshing would need to persist the new token back onto the `UserLeague` row, and the draft-session service has no DB handle to do that mid-poll today, so this is an intentional, documented gap (see `draft_assistant_service.py::_get_yahoo_draft_state`'s docstring), not an oversight.

**As noted above, none of this currently works end-to-end in this deployment** — Yahoo's own app console has a redirect-URI mismatch that fails the OAuth handshake before step 3 can happen. `credentials_configured` is `true` (client id/secret are set), so this is specifically a redirect-URI registration problem on Yahoo's side, not a missing-config problem on this app's side.

The old `live-draft/yahoo/authenticate` and `live-draft/yahoo/leagues` endpoints still exist in the code but are stale leftovers from before the per-user token architecture was built. `yahoo/leagues` in particular is currently broken: it calls `yahoo_service.get_user_leagues(season)` positionally, but that method's real signature is `get_user_leagues(access_token, season=2024)` — so the `season` value gets passed into the `access_token` parameter and no real token is ever supplied. Don't use these two for anything real; use `/api/v1/leagues/yahoo/*` instead.

## Draft Assistant Internals

### AI Recommendations — which pipeline actually runs

This is the most consequential correction to this guide. An earlier version described "Multi-Perspective Recommendations" — 5 angles (Conservative, Aggressive, Data-Driven, Situational, Dynasty) synthesized into a consensus — as if that's how each live draft pick gets analyzed. **That schema is real and current, but it does not run on live draft picks.** It's `ai_service.generate_multi_perspective_content` + `generate_consensus_recommendation`, and the only real callers are `content_generation_service.py` / `content_service.py` — the blog/waiver-post/player-spotlight content pipeline, not the live draft assistant.

What actually generates a live draft pick recommendation is `draft_assistant_service.py::_generate_ai_recommendations`, which calls `ai_service.generate_draft_recommendation` — a single DEEP-tier AI call (see model tiers below) that returns the top 3 recommended picks with reasoning and a confidence score in one shot:
```json
{
  "recommendations": [
    {"player_name": "Player Name", "position": "RB", "reasoning": "Why this pick makes sense", "confidence": 85}
  ]
}
```
This call is given the connected league's real `points_per_reception` and `scoring_rules` (when available — see "Real Per-League Scoring Rules" below) rather than just a bare "PPR"/"Standard" label, so the model can reason about e.g. a completion-accuracy league's QB values, not just reception scoring.

If you want the 5-perspective/consensus schema, it's real and worth knowing about for the content side of this app — just not for draft picks. It still works as originally documented:
- **Conservative/Risk-Averse**, **Aggressive/High-Upside**, **Data-Driven/Analytics**, **Situational/Matchup-Based**, **Long-term/Dynasty** — five separate DEEP-tier AI calls, one per perspective
- Then `generate_consensus_recommendation` synthesizes all five into one recommendation with `confidence_score`, `key_agreements`, `key_disagreements`, `risk_factors`, `action_items`

### AI Model Tiers and Fallback (consolidated this session)

`ai_service.py` was substantially reworked into one consolidated fallback primitive, `_generate_with_fallback`, that every AI-generation method in the file now routes through (previously `generate_multi_perspective_content`/`generate_consensus_recommendation` called OpenAI directly with **no** fallback at all — a rate-limited or unconfigured OpenAI client meant "OpenAI client not configured" could get embedded straight into what looked like real analysis).

Two model tiers per provider:
| Tier | OpenAI | Anthropic | Used for |
|---|---|---|---|
| FAST | `gpt-5-mini` | `claude-haiku-4-5` | Single player write-ups, waiver-wire blurbs — bounded, low-stakes |
| DEEP | `gpt-5.6-terra` | `claude-sonnet-5` | Draft-pick recommendations, the 5-perspective content pipeline, consensus synthesis — genuinely benefits from stronger reasoning |

Fallback behavior (`_generate_with_fallback`):
- Tries the `primary` provider first, falls back to the other configured one on **any** failure — rate limit, auth/billing error, network error, or the provider simply not being configured.
- Rate limits (`openai.RateLimitError` / `anthropic.RateLimitError`) are detected specifically and trigger an immediate, unambiguous fallback.
- An auth/billing failure on the primary does **not** short-circuit trying the secondary — they're different accounts on different providers.
- If every configured provider genuinely fails, returns a string prefixed `"AI generation failed: "` naming every provider attempted and why — callers check for this prefix before `json.loads()`-ing the response, so a real failure is never misreported as "failed to parse AI response."
- `GET /api/v1/... ` status: `ai_service.get_ai_status()` reports `openai_available`/`anthropic_available`/`primary_provider`/`fallback_enabled` based on which API keys are actually configured.

### Consensus Ranking System

`consensus_ranking_service.py` blends up to **four** independent, real ranking signals — this replaced every ranking surface in the app (Draft positional-rankings, Players list, live draft sessions) previously using exactly one signal in isolation:

1. **Sleeper `search_rank`** — public player pool, essentially every real NFL player, the baseline/default source
2. **ESPN `percent_owned`** — for a connected league's available-player pool, only present when a session has a live ESPN league
3. **Yahoo `ownership_percentage`** — only present when the batch being ranked is itself a live Yahoo session's available players (Yahoo has no publicly-fetchable player pool the way Sleeper does — every Yahoo endpoint is per-user OAuth-authenticated, so it can't cross-reference a *different* platform's session the way Sleeper/ESPN can)
4. **FantasyPros `rank_ecr`** ("expert consensus rank," aggregated across 130+ experts) — only present when `FANTASYPROS_API_KEY` is configured

Each source is converted to a **percentile rank within its own population** (0–100, 100 = best) before blending — raw values from different sources live on incompatible scales (a Sleeper rank of 12 isn't "close to" an ESPN ownership of 94.2 in any meaningful sense), so averaging raw numbers would let whichever source has the widest numeric range dominate for no principled reason. When multiple sources are available for a player, the consensus score is the unweighted mean of whichever percentiles are present — deliberately unweighted, matching FantasyPros' own published ECR methodology, since none of these sources has a principled claim to being more authoritative than the others. A missing source is never treated as "that source rates this player at rock bottom" — it's simply excluded from that player's blend, and `source_count` (0–4) on every result makes the degradation visible to callers instead of silently averaging it away.

### Real Per-League Scoring Rules

`app/services/scoring_rules.py` defines one canonical scoring-rules shape (`{"passing": {...}, "rushing": {...}, "receiving": {...}, "fumbles": {...}, "source": ...}`) that both `sleeper_service.parse_league_settings` and `espn_service_enhanced.get_scoring_and_roster_settings` populate from each platform's real, raw scoring settings — verified live against Sleeper's actual `scoring_settings` dict (`pass_cmp`/`pass_att`/`pass_int`/`pass_td`/`pass_yd`/`rush_yd`/`rush_td`/`rec`/`rec_yd`/`rec_td`/`fum_lost`, etc.) and ESPN's `Settings.scoring_format` statId list (cross-checked against the installed `espn_api` package's own id→abbreviation table, not guessed). This replaces the previous hardcoded PPR-only assumption everywhere: real leagues score pass completions/incompletions/attempts, INTs, fumbles lost, etc. independently of receptions — e.g. a real league can reward accurate/efficient QBs (`+0.5` per completion, `-0.5` per incompletion) in a way a bare PPR-vs-Standard label can't express.

`describe_scoring_rules()` turns a league's real scoring dict into a short, LLM-prompt-ready sentence (only surfacing rules that actually deviate from bare Standard scoring), which gets appended to the draft-recommendation prompt so the AI reasons about the league's real complete scoring picture. When no real per-league settings could be fetched (e.g. Yahoo's draft-state doesn't populate this today, or a fetch genuinely failed), `draft_assistant_service.FALLBACK_ROSTER_REQUIREMENTS` is used as an explicit, named fallback — and the code is careful never to pass that fallback to the AI prompt as if it were confirmed real data for a specific league.

### Manual Scoring Override

Real endpoints under `POST/GET /api/v1/league-scoring/*` (`backend/app/api/v1/endpoints/league_scoring.py`), backed by the `LeagueScoring` model:

- `POST /api/v1/league-scoring/configure` — create/update a hand-entered scoring configuration for a `user_league_id` you own (passing/rushing/receiving/kicking/defense rates, bonuses, completion-accuracy rules), then triggers `ScoringCalculationService.recalculate_player_points_for_league`
- `GET /api/v1/league-scoring/presets` — ESPN/Yahoo/Sleeper default presets
- `GET /api/v1/league-scoring/league/{league_id}` — current config for a league (or `has_custom_scoring: false` if none set)
- `POST /api/v1/league-scoring/compare-players` — compare specific players across multiple scoring configs
- `GET /api/v1/league-scoring/analysis/{league_id}` — how the league's scoring affects player values

Once a `LeagueScoring` row exists for a league, `draft_assistant_service.start_draft_session` layers it over whatever was auto-detected from the platform (`_apply_manual_scoring_override`, via `scoring_rules_from_league_scoring` in `scoring_rules.py`) — a manual override always wins over auto-detected platform settings, resolved once at session start rather than re-checked on every poll (the draft-session service has no long-lived DB handle to check it more often).

## Error Handling & Troubleshooting

### Common Issues (real, current)
1. **401 on `/start-session`**: missing/invalid `Authorization` bearer token — this endpoint requires auth even though several of the polling endpoints below it (`/recommendations/{id}`, `/draft-board/{id}`, etc.) currently don't.
2. **400 "No ESPN/Yahoo league connected for this league ID"**: connect the league first via `POST /api/v1/leagues/espn/connect` or `/yahoo/connect` before starting a session for that platform.
3. **400 "Your Yahoo connection has expired"**: Yahoo tokens live ~1 hour; reconnect via the Leagues page.
4. **"Session not found" (404)**: `session_id` doesn't exist in `draft_assistant.active_drafts` — sessions are in-memory only (not persisted to the DB), so they don't survive a backend restart.

### Debug Endpoints
```bash

curl -X DELETE "http://localhost:8000/api/v1/draft/live-draft/session/{session_id}"
```

## Frontend Integration

`frontend/src/pages/LiveDraftPage.tsx` is the real implementation — it derives its API prefix and WebSocket URL from one constant rather than hardcoding `ws://localhost:8000/...` per-call the way an earlier version of this guide's example did:
```ts
const LIVE_DRAFT_API_PREFIX = '/draft/live-draft'
// api.ts hardcodes its axios baseURL to http://localhost:8000/api/v1
const httpBase = api.defaults.baseURL || 'http://localhost:8000/api/v1'
```
It calls `api.post(`${LIVE_DRAFT_API_PREFIX}/start-session`, ...)`, `api.get(.../recommendations/...)`, `.../draft-board/...`, `.../team-analysis/...`, `api.post(.../update-pick, ...)`, and `api.delete(.../session/...)` — all through the shared axios instance in `src/services/api.ts` (which attaches the bearer token automatically), plus `GET /api/v1/draft/my-leagues` to populate the platform/league picker before starting a session.

## Advanced Features

### Custom Scoring Settings
The assistant adapts to a league's real scoring via the mechanisms above (auto-detected `scoring_rules`/`points_per_reception`, or a manual `LeagueScoring` override) — PPR vs. Standard, and now genuinely beyond just reception scoring. Superflex/IDP/custom-position handling is not implemented — `FALLBACK_ROSTER_REQUIREMENTS` and the roster-need logic assume the standard QB/RB/WR/TE/K/DEF position set; don't claim IDP support exists.

### League-Specific Analysis
- **Roster requirements**: adapted from real, connected-league settings when available (`roster_positions`/`FLEX_ELIGIBLE_POSITIONS` logic in `draft_assistant_service.py`), falling back to a named `fallback_standard` shape otherwise
- **Trade analysis / waiver recommendations**: separate features, covered by `trade.py`/`waiver_wire.py` endpoints, not part of the live-draft session itself
